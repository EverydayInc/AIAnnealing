# Annealing v01

<!-- markdownlint-disable MD013 MD060 -->

## Use when

Use for non-Standard work where materially different engineering structures, implementation approaches, or tradeoffs need independent model-family perspectives.

Do not use for exact active Standard Work, a single deterministic lookup, or work where another round has no named expected movement.

## Participants

Wilbur and Charolette are equal principal engineers on different model families. Neither is the permanent implementer or reviewer. The operation records exact agent IDs, model/builds, runtimes, instruction hashes, and this skill hash.

## Preconditions

1. Freeze one byte-identical current-reality brief.
2. Include outcome, source revisions, constraints, non-goals, acceptance, effects, risks, falsifiers, and operation bound.
3. Verify both model families and runtimes are available.
4. Explicitly name the first lead and, if software is in scope, the first writer.
5. Do not infer first writer from personality, prior habit, or artifact type.
6. Give neither principal the other's first answer before both are frozen and hashed.

## Independent openings

Each principal returns a complete position:

- decision;
- evidence and assumptions;
- design and implementation shape;
- rejected alternatives;
- risks and reversibility;
- tests and decisive experiments;
- first useful piece;
- falsifying evidence;
- human choices.

## Design rounds

After both openings are frozen:

1. Lead authors a new complete synthesis.
2. Partner critiques the exact hash.
3. Partner authors the next complete revision.
4. Prior lead critiques it.
5. Continue only while the next round names material expected movement.

No permanent critic chair. No manufactured consensus.

## Software rounds

Software includes code, tests, configuration, migrations, policy-as-code, build definitions, and deployment definitions.

1. The named writer owns one isolated revision and runs its checks.
2. The reviewer receives a frozen exact revision and does not edit it.
3. Blocking findings identify exact behavior, path/symbol, evidence, and acceptance.
4. If revision is required, the prior reviewer becomes writer of the next revision.
5. The prior writer reviews that new revision.
6. Neither principal approves, merges, releases, deploys, or accepts human-owned risk.
7. Retain every base, patch, result tree, check, review, and disposition hash.

For the first Everyday MCP connector operation only, Charolette is first writer and Wilbur first reviewer to correct accumulated Wilbur-default behavior. This does not set a permanent order.

## Pareto check

At each completed round, invoke the configured Pareto agent or explicitly disclose if unavailable. Pareto evaluates material movement and return conditions; it does not become a third solution author.

Return after:

- two consecutive dry rounds;
- no named expected movement for another round;
- the declared round bound;
- missing human grounding, evidence, authority, or preference;
- a provider, policy, safety, or control stop.

## Output

Return a standalone package with current artifact, movement, evidence, experiments, disagreements, decisions, risks, reversal, participant/model lineage, software writer/reviewer lineage, reason for return, restart seam, first useful trial, and PDSA.

## Boundary

The skill coordinates reasoning and bounded sandbox artifacts. It grants no Multica workflow mutation, GitHub write, merge, deployment, provider, credential, production, policy, or risk authority.
